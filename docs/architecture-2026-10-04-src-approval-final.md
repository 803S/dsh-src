# SRC 审批闸最终架构选型（基于本机条件验证）

日期：2026-10-04。状态：架构选型确定，尚未完成产品实现/安全验收。
本文件收敛此前完整规划的工程选型；安全不变量不放宽。实测见 `docs/evaluation/egress-feasibility-20261004` 与 `docs/evaluation/egress-extended-20261004`。

## 1. 结论

选用 **DSH 专属执行器约束 + 复用 mitmproxy + 现有 SRC 决策/审批服务**。

不引入虚拟机、全局代理、全局防火墙、第二套审批平台，也不自行编写 HTTP/TLS 协议栈。本地文件权限继续使用 DSH 原生策略。控制系统私钥/配置等不可被模型改写，这是本系统完整性保护，不是对普通项目文件加审批。

本机条件已验证：bash 进程网络限制、子 shell/后台/Python 的基本继承、HTTPS 内容可见性、独立于 full-access 的网络约束、本地 TCP/Unix socket 直连拦截、合成控制目录保护。不能据此推导所有协议、工具、IPC 和 OS 逃逸路径已验证。

## 2. 最终组件

```text
                    DSH 主/子代理
                         │
        ┌────────────────┼──────────────────┐
        │                │                  │
  SRC 内置网络工具   SrcShellExecutor   专属浏览器/MCP适配
        │             最终启动约束          │
        └────────────────┼──────────────────┘
                         │ HTTP/HTTPS＋绑定会话的投递身份
                         ▼
               DSH 管理的 mitmproxy
         TLS/HTTP解析、完整缓冲、不私自跟随跳转
                         │ 发送前向 SRC broker 请求决策
                         ▼
                现有 DSH/SRC 控制面
           scope → Jev＋硬规则 → 现有审批数据库/UI
                         │
          allow / pending / reject / approved-execute
                         ▼
           统一调度、限速、上游发送、证据记录
```

### A. SrcShellExecutor：管住实际启动，不审命令文本

正式实现一个版本化的 SRC executor/provider，复用原生 BashExecutor 的进程、超时、输出、后台任务和文件策略。在最终生成 spawn argv 处附加独立网络约束。

- 对 workspace-write/read-only：在原生 profile 中组合约束；对 danger-full-access：保留不限制普通文件的原意，但独立网络规则仍存在。
- 不能只包装 sandbox.confine，因为原生 full-access 不经过它；本轮真实 ToolRuntime 已验证最终 spawn seam 可以覆盖该路径。
- 注入代理与公开 CA 配置用于客户端兼容；这些配置被删后只能连接失败，不能直连。
- 加载时验证 DSH/OS 版本、实际 runner 和最终执行测试；不满足则拒绝 SRC 外发，不静默退回 LocalBashExecutor。
- 正式安装用可追踪包/扩展和固定兼容版本；实验中的内存方法包装不直接作为产品交付。
- PTY/持久终端、能力脚本、浏览器/MCP 子进程都需显式适配最终启动路径，不能假设自动被 bash 接管。

### B. mitmproxy：只负责协议和发送，不拥有人工授权权力

复用本机已有、可固定版本的 mitmproxy；正式部署检查依赖版本。默认一个 DSH 实例按需管理一个代理进程，不按请求启动进程或模型。无活动 SRC 任务且无执行中操作时退出，避免长期占内存；pending 单存在数据库，不必保持 curl 连接。

共用监听端口需要使用受信启动器签发的短期、限定 engagement/session 的**投递凭证**。它只用于提交待判请求，不是高危批准凭证。网关验证后由身份记录确定归属，不相信自报 sessionId 请求头。不能由其他会话盗用或枚举；跨进程环境读取/控制文件访问必须验收。若不能可靠保护该绑定，不得以共用端口方案上线。

- 逐请求完整检查 HTTP/HTTPS；不转发原始盲 CONNECT，不开放通用上游代理地址。
- 完整缓冲与大小/解压/超时限制，超限拒绝；不能先发送再分析。
- 会话级公开 CA 信任，不安装系统 CA；上游证书照常校验，特殊目标证书例外需显式授权。
- 重定向后每个请求重新过闸；Host/SNI/URL 歧义或协议解析冲突拒绝。
- 原始请求 hash、发送请求 hash 和 Jev 审核摘要绑定。严格保护原始凭据；发给 Jev 的内容仅保留风险必要的脱敏语义，关键语义丢失则不自动放行。
- 插件配置固定禁用流式透传、ignore-hosts/TCP 任意转发等逃生选项；不使用用户已有的全局代理配置。
- HTTP/2、WS、HTTP3 等未通过逐消息/逐请求验收前不开放，客户端可走已支持的 HTTP/1.1；无法安全兼容则明确不可用。

### C. SRC broker：复用现有能力，只有一套审批真相

broker 放在现有 DSH SRC 控制面，不另起业务微服务；复用 Jev client、SQLite、事件/证据存储、审批 UI 和人工命令。

每个可检查请求由 broker 做 scope、Jev、确定性风险规则、累计预算与安全计划判断。明确危险不能被 Jev allow 覆盖；语义未知/矛盾/超时转人工；越界或协议不支持拒绝。关闭 Jev不能回到旧的宽松自动发送路径。

批准绑定冻结请求、会话、账户引用/版本、范围/策略版本、安全材料和有效期。数据库事务领取发送权，不再让主模型持 grant 重新拼接请求执行。

审批控制 API 与代理投递 API 分离。执行进程不能直连控制 API；通过代理访问它也必须被 scope 拒绝。人工批准密钥/凭据、服务配置和部署代码禁止执行面读取/改写；原生 read/edit 工具也需遵守对应保护，不能只挡 bash。

共享限速/并发/Jev 队列有界；目标慢/Jev 错误/存储不可用不降级发送。危险操作发送后断线记 outcome_unknown，不自动重发。用户批准不免除 XML/文本/JSON 对等的写前保护与写后验证。

## 3. 工具兼容边界

- src_http、扫描、凭据测试等：目标 transport 统一经此出口，原工具内重复 Jev 判定移至 broker；模型看到的工具 API 尽量不变。
- shell：继续用 bash，不新增“安全 curl”工具要求模型选择。
- 浏览器：只使用 DSH 启动的专属受约束实例；不能接用户普通浏览器绕行。
- Burp/MCP：纳管其真正发包端；只约束 stdio 桥而 Burp JVM 能直连不算纳管。不能约束的现有共享实例保留只读能力、关闭目标发送，不中断用户手工 Burp。
- 远程 MCP 和非 HTTP 协议：本地代理不能控制远端执行，未有可信适配就不开放目标操作，不拿“已调用 MCP”当已过闸。
- 公共资料查询通过独立受控能力；不能让 shell 以“非目标域名”为理由访问任意外部转发器。
- 平台 Apple Events/Mach IPC、跨进程控制和启动系统服务等代发途径仍需要专门收敛与验收；本轮本地 TCP/Unix socket 测试不能替代这些结果。

## 4. 审批交互

1. 请求先冻结、检查。低风险且无硬边界冲突则放行。
2. 高危/未知创建 pending，代理向客户端返回明确的 SRC_GATE_PENDING 与 requestId，不伪装目标响应。请求未到达目标。
3. 用户在现有 SRC 面板看目标、动作、账户、差异、备份/恢复条件与风险来源，批准或拒绝。
4. 批准后 broker 校验请求仍有效，驱动网关执行保存请求并记录结果；取消/过期/对象变化不得自动执行。
5. 模型收到状态通知或查询原 requestId，不需要再用 curl 重试；拒绝记录保留，不能通过再次调用 Jev抹去拒绝。
6. 写入不能保证服务端“恰好一次”；只能实现事务领取、不盲重发和对不确定结果诚实记录。

## 5. 本轮验证结果与可信度

| 层次 | 结果 |
|---|---|
| 上轮真实 DSH 主模型 + HTTP/workspace-write | 6 次 bash，指定读取成功、直连/脚本/后台被阻止、本地文件正常 |
| 本轮 19 个确定性原生沙箱/TLS/控制端场景 | 预期对照成立，见 deterministic.json |
| 本轮真实 DSH ToolRuntime/full-access/HTTPS | 8 次调用与8次启动约束；目标只收到2项允许请求及1次初始重定向 |
| 本轮主模型/full-access/HTTPS | 未执行指定测试，验收失败/未覆盖；没有用0请求当成功 |
| Jev + 真实人工审批、生产部署、全通道、负载 | 未在本轮验证，不宣称已完成 |

本轮代理采用固定的合成拒绝规则，因此只证明传输和执行接入条件，不证明 Jev 对真实请求的风险准确率。完整旧规划中的人工身份、请求绑定、失败关闭和写安全要求仍属于正式实现验收门槛。

## 6. 工程规模与上线决策

主要新增：一个 SRC executor/provider、一个 mitmproxy addon/管理器、一个集中 broker 模块。审批存储和界面修补复用，不扩展成新的平台。无新增常驻本地推理模型。新增 Python 代理进程的实际 RSS/负载开销尚未测量，不承诺零开销或具体内存数字。

这次实验支持选择轻量架构，不支持跳过后续安全实现验证。发布前必须完成：

- 真实主模型完整 prompt 验收和真实人工批准/拒绝；跨会话投递/审批身份不可伪造。
- 自动提权、后台/PTY、所有开放工具发送端、系统 IPC 代发路径均不能绕过。
- 网关/DSH/Jev 故障、并发、取消、重启与未知发送结果正确处理。
- 所有外发都有决策与证据；原始秘密和部署完整性不受模型控制。
- 原生文件权限语义回归、代理资源成本测量、安装/版本升级/安全回滚验收。

任何未纳管通道不得默认开放；若用户必须使用它，就先补适配和验收，而不是提示词劝阻或放行直连。当前仅确定架构和可行性，生产系统尚未部署这些约束。

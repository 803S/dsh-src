## 0. 结论先行

项目确实存在职责、数据流和验收流程膨胀，但不是“文件多所以卡”。本轮已确认最大的切换卡顿来自：

> 旧 SRC 全量状态读取产生了大量命令历史 → 对话组件把巨型单行 JSON 当折叠摘要完整渲染 → 切回对话同步读取 scrollHeight → 强制布局卡住约4.4秒。

CVE会话真实Chrome对照：不修改历史、不修改磁盘，只在测试浏览器中将通用命令卡摘要限制为240字符，SRC→对话由 **4476–4629ms降至141–154ms**。这是本轮最强的因果证据。

优先顺序应是：

1. 修历史大结果的展示与新的大结果输出，不删会话、不靠裁证据掩盖卡顿。
2. 统一Git提交、构建、安装包、部署文件真相，阻止再发不一致版本。
3. 修待办的确定性状态写入、入口信息和实际续接；禁止把审批复制为待办。
4. 将审批收敛为“完整操作评估＋执行一致性校验”，保留必要边界，去掉分散业务政策。
5. 再做存储、模块、能力安装、文档及仓库结构治理。

不承诺靠一次重构“消灭所有bug”。本方案覆盖已发现问题，使用明确验收矩阵关闭；未知问题持续通过性能与业务指标暴露。

## 2. 切换性能：已实证主因

### 2.1 环境与结果

- 会话：`session-bda5bad4-7c0b-44bf-a315-0a593aba6565`，标题CVE-2023-27372。
- Web PID93814，检查时427会话idle；采样时Web进程CPU约0.1%，不能据单次采样推断持续负载。
- Chrome，1440×1000，本地3080；只操作视图、不执行目标工具。

| 操作 | 本轮耗时 | 备注 |
|---|---:|---|
| 热切对话→SRC | 76/82/89/90ms | 首次一次4170ms含加载/排队，不能混为热切耗时 |
| SRC→对话（5次） | 4467–4763ms | 每次4377–4645ms主线程长任务 |
| SRC内部timeline/todos/overview | 96/84/66ms | 单次样本，不代表完整分布 |
| SRC→对话（原版A/B样本） | 4629/4476/4626ms | 同机同会话 |
| SRC→对话（浏览器摘要截断） | 141/154/154ms | 未改历史/数据库/服务端 |

热切期间WS新帧字节为0。整个测试所见少量WS帧不能代表初次HTTP历史载荷；只足以说明每次4.5秒热切并不是在等新增WS数据。

### 2.2 原始数据规模

- CVE session.jsonl.zstd：约7.94MB压缩，**138,414,787字节解压后**。
- `src-authoritative-state`：112条 `command/done`，文本累计 **120,750,384字节**，最大单条1,332,618字节。
- 约87%的解压会话字节量可归于这些重复命令结果；这不等于模型实际接收的token量，不能混淆。
- 对话DOM可见文本约 **50,070,850字符**；42个大于10万字符的文本节点，最大1,305,918字符，位于 `SPAN._Xvjua_summary`。
- 原版DOM约5881元素；SRC约593元素。问题不只在节点数量，更在单个文本节点极大。
- 仅截断命令摘要后：页面文本46,249字符，没有大于10万字符的摘要节点。

### 2.3 调用栈与归属

实际浏览器加载的 `@deepseek-ai/dsh-client-ui-conversation/client.js`：

- `GenericCommandCard` 约9490行：`summary`直接使用`node.outcome.text`；只有包含换行才生成可展开body。单行巨型JSON因此完整进入collapsed summary。
- `toBottom` 约5588行：`el.scrollTop = el.scrollHeight`；在useLayoutEffect中触发布局。CPU采样约4383ms记在此处，是强制布局的触发点，不证明函数自身做了4383ms JS运算。
- 来源为上游宿主对话组件，但大文本由本项目之前的全量状态命令产生。**两边都要修，不能全推给宿主，也不必重写宿主压缩策略。**
- 皮肤插件在该profile中不是主热点。没有证据支持先卸载皮肤解决这次卡顿。

### 2.4 性能修复设计

**止痛修复，先于大重构：**

1. 通用命令卡collapsed summary按字符/字节有界（例如240–500字符）；不以“有无换行”决定是否可能为大结果。
2. 大正文只在明确展开时懒加载、分页渲染；禁止给title属性/隐藏DOM再塞完整MB文本。需要全文时提供只读详情/下载。
3. 使用宿主支持的command card扩展点；若无扩展点，提交明确上游补丁或固定版本的最小兼容补丁，带源码hash校验、安装与卸载记录。不要直接手改全局bundle作为永久方案。
4. 不再通过会话命令传送整份SRC状态：查询走只读API/projection；命令返回简短结果或artifact引用。`recordInput:false`仅隐藏输入，不禁止command/done结果留史。
5. 旧历史以展示层有界处理立即获益，不需要删除112条旧记录。历史归档/迁移另行设计并备份，默认不开破坏性重写。
6. 对话视图滚动定位与挂载优化仅在摘要修复后测量；避免先重写虚拟滚动系统。

**后续数据层：**

- 实时projection传实体概要、计数和最近索引；HTTP正文按observation ID查询，分页/取消/缓存隔离。
- 禁止简单只保留最近160条而没有“更早记录”入口；也禁止用子集数量计算全局覆盖率。
- 减少重挂载与重复全量计算，但缓存必须按sessionId＋revision隔离，不能把上一会话审批按钮带入下一会话。

## 4. 发布一致性：P0缺陷

### 4.1 本轮核对

local.128 HEAD、tgz、两个profile中：

- `lib/src/egress/manager.js`：**Release不等于HEAD，Release等于两个部署副本**。
- 差异是扩大failed-before-send恢复条件的未提交修改。
- `lib/ui-src.client.js`：Release等于HEAD及部署副本，但其源TSX/CSS有未提交改动。前次发布时构建产物与对应源码未形成完整闭环。
- 当前多个文件有未提交改动，不应再次直接npm pack并称为某个干净tag的产物。

### 4.2 当前发布脚本缺口

`deploy.mjs`：

- 会跑npm test，但不强制UI typecheck/build/browser test，也不要求工作区干净。
- 从工作目录直接复制，不从不可变的已核验安装包部署。
- 就地覆盖多个profile/桥接文件，非原子切换；失败时可能混合版本。
- 不移除旧版本已删除文件，旧安装路径可残留。
- 版本号和MD5文件一致只证明复制一致，不证明“HEAD＝包＝部署”。

`start-dsh-web.sh`：

- 有idle检查，但默认重启参数仅`web --no-open`，与实际服务的host/port/trusted-host不同。
- 过去手工重启又使用不同cwd，启动入口不统一。

### 4.3 必须建立的新发布契约

1. 开发完成→全部检查→明确提交文件清单→干净main（允许的本地产物必须被忽略）。
2. 从提交导出临时构建目录（不是新增Git worktree/分支），锁定依赖构建、测试、打包。
3. 产物manifest包含commit、源码/配置schema版本、工具链版本、运行文件SHA256。
4. **同一个tgz**用于干净安装测试、本机部署和Release上传；禁止分别从工作目录复制和打包。
5. 两profile先staging验证，再在确认idle后可回滚切换；备份原副本，保留原启动参数。
6. 显示实际commit/build hash，不只显示local版本字符串。
7. 不重写local.128已发布tag或force push掩盖差异；追加纠正说明，下一个版本建立一致来源。

## 6. 安装包与可复现构建

已发布local.128包：198文件，压缩约2.085MB；解包分类：

- lib约1.812MB；images约1.358MB；顶层docs约562KB；scripts约147KB。
- `files`包含`docs/*.md`，却没有嵌套implementation/evaluation。README中本次检测到14处相对文档引用在包内不存在。
- 包带deploy脚本，但该脚本依赖的`plugins/`等源码不在包里。源码安装与tgz安装的能力集合没有统一说明。

- 前端bundle无minify、无sourcemap。压缩可减少下载，但不是本次4.5秒布局主因；sourcemap可作为受控调试产物。

## 7. 审批、Jev、工具入口的结构性优化

详细依据见 `audit-operation-approval-boundary-20261009.md`。这里明确优化目标而非继续添例外：

### 7.1 统一操作记录

利用现有store/broker/工具运行时，不新增常驻调度平台。操作记录至少关联：

- operationId、session/intent、真实调用工具与来源；
- 用户任务和主模型给出的理由（标明为模型解释，不是授权）；
- 命令/参数/脚本正文、必要输入文件版本及内容摘要；
- 明确目标origin、账号/测试对象上下文、次数/速率/预算；
- Jev判定及失败种类、人工决定、执行阶段、实际证据及后续动作。

理由、命令和实际报文一起进入审核；当前代理入口丢理由、Burp把用途换成通道说明必须修正。附件采用类型感知表示，不能把二进制UTF-8解码失败当高危判定。

### 7.2 一次风险评估，不同适配

- 工具名不决定危害；规则筛查确定边界与风险信号，Jev复核局部语义，高危/不确定由人工决定。
- 相同已核对条件下src_http/curl/脚本/浏览器/Burp风险结论应一致。
- 执行校验继续检查原文/目标/文件版本/预算没有偏离，不再次否决同一已批准的业务风险。
- 不因“当前没适配”“不支持WS”“服务超时”标成高危：能力不足、基础设施故障、风险不确定、越界分别展示。
- 对正常浏览器子资源使用已审核的有界操作策略；不能无限放行同域所有请求，也不逐个CSS弹人工审批。

### 7.3 原工具执行与恢复

目前本地403中断原工具、批准后宿主补发HTTP，不等于原脚本/浏览器完成。需明确两种方式：

1. 优先在原工具开始前审核并执行；命令/脚本快照、输入版本及预算绑定。
2. 运行中才出现的动态动作分阶段暂停，保留可恢复上下文与结果；若必须宿主接管，明确告知原工具结束、提供原始结果和后续任务，不假装脚本已继续。

重试策略按发送证据和操作幂等性设计；不把“人工批准”写成“客观无危害”。对未发送可恢复、明确幂等且预算允许的操作可受控重试；对可能已产生副作用但结果未知的请求核对后再决定。当前并没有通用自动恢复调度器，不应继续宣传已有。

### 7.4 测试对象语义

- 测试文件上传、修改、删除，以及明确可丢弃的测试账号/记录应按实际影响分类，而不是按方法词。
- 现有ETag/If-Match文件模型只是归属证据的一种，不能当所有业务都必须实现的协议。
- 支持用户明确的测试身份/资源范围以及真实创建响应、ID和后续读取的证据；不能由模型一句“自己资源”自动获得授权。
- 普通业务账号的级联删除/共享空间、真实费用/对他人通知仍应明确提示并交人工。

## 8. 审批与待办不重复、账号协助形成闭环

### 8.1 已确认问题

- `src-todo` 当前主要followup要求模型再写状态，不是点击即持久化；投递异常/模型不响应时会表现为“点了没后续”。
- `store.upsertUserTodo` 校验intentId但新建未保存；更新未知ID会落入新建，不是明确not-found。
- 当前未提交的防重复尝试只看title中pending审批号，既会漏detail，又可能把approval-1误匹配approval-10；不能发布为完成修复。
- 当前targetUrl添加尚未完整进入工具schema/要求/legacy fold；字段存在不等于功能完成。
- finalize提示要求blocked必建todo，没有完整承认“已有审批”这一等待类型，诱导重复劳动。

### 8.2 设计

1. operation/intent显式引用等待原因：approval、user-input、technical-block；审批本身就是用户决定事项，不再复制todo。
2. todo保留给账号登录、真人交互、提供资源等实际人工工作。创建时传关联intent，已有同项复用；不能用一句不精确关键词禁掉所有有审批号的账号协助。
3. 账号类记录：目标完整URL、已确认登录入口、注册入口及来源、账号数/角色、用户需要做什么、完成后系统准备做什么。未知注册入口标“未找到”，不能编造`/register`；可提供已验证登录入口并说明需管理员创建。
4. 点击完成/放弃：可信用户命令先校验ID并持久化，更新projection，再投递带todo/intent/URL/动作的续接事件。
5. 完成不等于验证成功：完成登录后实际拉Burp/导入凭据/测试有效性；失败回报具体原因。放弃后只撤销依赖该输入的测试分支并记录覆盖限制，不自动放弃整个任务。
6. 记录通知状态：待投递、已入队、模型已消费、验证结果；投递失败有“重新通知”入口且不重复改状态/发目标请求。利用现有followup/事件机制，先不另建调度服务。
7. 旧记录只读显示“缺入口/缺关联”，允许补充；自动整理重复todo要有preview/用户确认，不能静默删除历史。

## 9. 存储、projection和证据成本

### 9.1 当前规模

SRC数据库：922条observations、971条src_commits；observations JSON约5.30M字符，commits约5.93M字符。SQL length(value)为字符数，不是磁盘字节。

CVE：532条observations（1.28M字符）、627条commits（1.73M字符）；3 intents、5 facts、1 finding、16 coverage、5 todos、10 approvals。

### 9.2 成本点

- sessionData对多张全表entries做数组化、filter、sort；一个会话读取会遍历其他会话数据。
- 每次mutation前后captureRows扫描14张表，并对会话记录JSON.stringify比较；还扫描全部commit找下一seq。
- SQLite backend loadAll同步读取/解析所有记录；putRecord逐条JSON序列化，无领域多行事务。
- 证据正文在observation、commit日志、会话合成事件及历史全量command中重复。
- managed src_http可能产生出口证据与工具层证据两条，扫描也有raw＋scan；这些是层次重复，不等于独立测试次数。

本轮只读内存微基准：12,326行、CVE595条projection相关记录，capture两次＋无变化diff中位约3.04ms（20样本）。**不是当前4.5秒主因**，但规模增长/并发下有成本，列P2而非以它替代P0。

### 9.3 优化

- 先在现有store维护session→row索引、ID计数与seq计数，避免每次全表扫；写入/删除同步维护索引并测重开恢复。
- mutation记录实际dirty keys形成增量commit，不再每次整份字符串diff；保留一次legacy baseline迁移路径。
- body大对象进入证据存储，projection/commit携引用与摘要；保留可追溯hash，不丢正文。
- 多表状态＋事件提交采用明确原子边界或可恢复提交协议；SQLite改动配套迁移和回滚演练。
- 区分dispatch/response/evidence，按dispatch统计真实请求，不按observation行数吹覆盖。
- 先在只读副本/合成10倍数据测指标，禁止直接清理生产DB“压小”。

## 10. 主模型、子代理与研究流程

- 目前delegate开关注释称advisory-only，src_add_intent已自动调用child；角色又用标题正则选。必须统一对外契约。
- 推荐、主模型选择、派发、启动、检查点、完成/失败分开记录；不以成功入队标任务完成。
- 主模型负责完整有界任务合同、依据、停止条件与资源预算；Jev做简单分类/建议，不能悄悄接管复杂规划。
- 防重复派发必须有并发幂等键；失败后显式接管/恢复，不能吞异常后仍显示成功。
- skill路由附加不等于实际采纳；有read和实际使用证据才记采纳指标。
- nDay流程需“指纹→官方/可信公告→版本范围/前提→基线→有界验证→证据→独立复核”。搜索失败不等于漏洞不存在，也不能用猜测路径404排除CVE。
- 公开资料检索与目标主动测试分离，不能要求把NVD登记成靶标才能读公告；限制资料通道凭据、协议、重定向和主动动作，而非封掉研究。
- 不能承诺模型一定发现所有漏洞；验收看指定合成/授权基准能否走通及误报/误拦率，不看finding数量KPI。

## 可维护性审查

### 摘要

维护风险主要是既有审批管理器与验收入口过度集中、部分关键条件压成单行。本轮只做必要行为修复，不为代码风格引入新层、新服务或大规模拆分。以下建议均保持现有行为。

### P1：管理器承担多个生命周期——中

- **原则/位置**：函数单一职责、结构清晰度；`lib/src/egress/manager.js:22–545`。
- **问题**：范围持久化、代理生命周期、待审发布和人工恢复集中在一个工厂闭包，修改时容易漏掉共享状态。
- **建议**：后续修改相应路径时只提取现有职责的局部纯函数，保留同一状态所有者，不增加抽象服务层。
- **当前风险**：容易出现“发布时检查了、最终执行忘了再检查”的遗漏；本轮已把新增阻断放到最终事务。

### P2：测试入口的巨大条件表达式难核对——中

- **原则/位置**：结构清晰度、DRY；`scripts/egress-feasibility/managed-run.mjs:254`。
- **问题**：多个场景到达集合堆在一条表达式里，失败原因难读。
- **建议**：将既有预期集合命名，不改变任何场景、次数或顺序断言；不新建测试框架。
- **当前风险**：容易把模型步骤差异误报为出口缺陷；本轮所有失败均保留并人工核对实际发包。

### P3：兼容字段名称与实际语义有差异——低

- **原则/位置**：命名、项目规范；`lib/src/egress/broker.js:41`。
- **问题**：历史字段 safeRead 现表示“明确无副作用的读取或计算”。
- **建议**：保留持久化字段兼容，在计算位置写清语义；本轮已补注释，不为改名迁移账本。
- **当前风险**：以后若再按GET理解该字段，可能重新引入POST误拦。

其余维度：DRY以现有统一冻结/审批链为准；YAGNI未新增层、依赖或表；`plan.js:5`的预算已有统一LIMITS，`manager.js:55`的缓存数量可在触及该处时命名而不改数值；中文更新记录与仓库外测试产物约定保持。未发现需要本轮大重构的证据。

### 值得保留

- 冻结原参数、批准与原请求绑定、最终领取事务检查和持久化次数。
- 人工等待与执行预算分离；只挂起对应操作；拒绝/未知不通过重试洗白。
- 同时核验正常到达与危险零到达，固定桩和真实模型证据分开。

### 边界与后续测试缺口

- 30天等待是注入账本时钟并真实重启，不是实际等待30天。
- 本轮实际OS验证是macOS；其他平台的内核隔离不据此宣称实测通过。
- 现有危险关键词硬规则仍保守，可能把含相关词的正常业务路径送人工；没有为通过合成用例放松它。未知业务副作用不能保证由Jev百分之百识别。
- Burp用户手工操作、扩展额外行为不属于AI工具参数审批保证；不承诺任意工具新增入口天然安全。
- 后续维护上述大函数时，应保留取消/并发、同请求旧授权、跨进程、单次发包与待审后独立工作测试，而不是再加一套审批框架。

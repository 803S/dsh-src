# local.124：审批生命周期复审

## 摘要

local.123 的局部修复仍留下了跨路径、跨状态的问题。本轮新增复现确认五处缺陷：自动路径漏审辅助请求、主操作失败误锁独立读取、拒绝落库后取消造成半完成状态、未发送的中断批准无法放弃，以及审批与结果核对并发时写出矛盾状态。修复集中在现有 broker、manager、ledger 和审批卡，不新增依赖、数据库表或后台服务。

## 已复现并修复的问题

| 级别 | 触发条件与旧行为 | 修改与实际验收 |
| --- | --- | --- |
| 高 | 计算请求携带前置/回读，整组获自动放行时，绕过 local.123 仅在人审路径调用的独立检查 | 自动与人审共用 `assertHostExecutable`。自动路径在建立授权前核验；旧版未发送的自动计划首次执行前补核验。危险检查零到达，正常检查和正文按序到达；相同检查只判定一次。 |
| 高 | 主操作断连后，`quarantine` 连同只读辅助请求一起封锁；用户无法读取状态来核对结果 | 主操作结果未知只隔离主操作；辅助请求自身断连仍独立保留保护。人工核对整单时处理本单辅助锁，其他任务的锁保留。原主操作不重放，独立读取实际成功。 |
| 中 | 拒绝记录已持久化，回合恰好取消，执行账本仍为 pending | 持久拒绝继续完成不发包的账本变更；旧版半完成拒绝只允许继续拒绝。真实 DSH 命令在落库后取消，最终账本仍为 denied。 |
| 中 | 已写入 authorized 但未发送时中断，旧代码只能继续批准，无法拒绝放弃；审批卡也没有入口 | 零使用、无工具启动、无发送证据的中断批准可继续或拒绝；已有使用记录时仍拒绝恢复。冷启动与并发用例通过。卡片显示继续/拒绝入口、具体错误和核对路径。 |
| 中 | 人审正在等待辅助请求判定时，同时核对撤销旧单；随后人审写入 approved，账本却已 reconciled | 补材料、审批、结果核对共用同一审批编号的操作锁，锁在首次异步等待前取得。旧版复现允许并发核对，新版拒绝竞争操作，胜出的请求仅实际发送一次。 |

入口命令不再复制 manager 的恢复状态条件；仍先验证可信用户来源，最终资格由冻结请求和执行账本判定。未知/失败/中断记录不再使用成功色，也计入需要处理的事项。查看页面不会批准或重试生产请求。

## Clean Code 检查

### Summary

近期反复出错的直接原因是同一审批约束分散在自动执行、人审、恢复、命令入口和界面中；一种路径修好，并不意味着相邻路径也经过了相同校验。本轮把执行材料检查和单审批互斥收回共用入口，并以实际发送结果验证状态衔接。

### Findings

#### P1：审批条件分散在多个入口

- **原则**：DRY、单一职责。
- **位置**：`lib/src/egress/broker.js` 的 `assertHostExecutable`，`lib/src/egress/manager.js` 的 `lockApproval`，`lib/src.js` 的 `/src-approve`。
- **级别**：高。
- **问题**：自动、人审、恢复与命令入口曾维护不同的条件集合。
- **建议**：保留本轮共用检查；后续只对状态判断抽取纯函数，不再次复制授权规则，不改变现有行为。
- **Why now**：已经产生自动路径遗漏和旧单入口拒绝的问题。

#### P2：manager 承担过多生命周期职责

- **原则**：函数规模、结构清晰度。
- **位置**：`lib/src/egress/manager.js` 的 `createEgressManager`。
- **级别**：中。
- **问题**：范围持久化、代理管理、审批映射和发送阶段在同一闭包中，错误处理容易遗漏跨状态影响。
- **建议**：后续按现有边界提取纯状态判断与展示转换，保持账本事务和发送入口不变；本轮不做大规模拆分。
- **Why now**：新的修改必须同时检查取消、持久化和发送三个边界，不能继续只加局部条件。

#### P3：界面“已批准”混同执行结果

- **原则**：命名、结构清晰度、项目规范。
- **位置**：`src/dsh-client-ui-src/src/client/ActionCenter.tsx`、`approval-explanation.ts`。
- **级别**：中。
- **问题**：批准后尚未执行、执行失败与结果未知都可能采用成功色并从待办计数中消失。
- **建议**：保留 `approvalNeedsDecision` 与 `approvalNeedsAttention` 的区分；界面只展示可操作入口，实际权限仍由宿主核验。
- **Why now**：只看到“已批准”无法判断请求是否真的发出，也找不到后续处理入口。

七个维度均已检查：命名、函数规模、重复、过度设计、魔法数字、结构清晰度、项目规范。本轮未为过度设计、魔法数字和 import 风格另列低收益修整项。

### Good Patterns To Keep

- 冻结实际请求、精确预算、每次发送领取和结果未知禁止重放。
- 用户决定与模型目的说明分开；范围确认不等于高危操作授权。
- 辅助检查先核验实际语义；独立低影响工作可继续。

### Test Gaps

任何后续审批修改都要同时验证：自动与人工、成功与失败、正常与取消、热运行与冷启动、单次与并发、原请求与辅助请求。不能只用“按钮可点”或“返回 approved”作为验收；必须核对靶场实际到达、账本状态及旧单的可处理性。

# local.122：修复批准后被旧资源锁拦住

## 已复现的原因

三张原审批均为 `approved / failed-before-send`，错误为 `SRC_GATE_RESOURCE_REQUIRES_REVIEW`。生产备份显示同接口存在一条旧请求的 `outcome_unknown` 锁；不是三张待审单互锁。local.121 只增加了人类确认和安全说明，没有将该次确认传递到请求领取阶段，导致用户批准后仍被接口级锁拒绝。

## 修复

- 可信人类确认绑定本笔精确请求摘要；领取阶段将其视为独立低影响请求，与既有明确只读路径使用相同的资源隔离规则。
- 仅绕过其他操作的接口级牵连，不删除原锁、不改变 Jev 原始判定。同请求、同操作、人工拒绝、未知结果、范围变化、请求预算等检查仍执行。
- 原三张失败单提供“核验未发送并重试”。后端须验证原批准记录、错误类型、冻结原文、当前范围、单笔预算、已用次数为零、无任何发送记录、无工具启动，才能恢复原编号；已有发送证据即拒绝。
- 查看、启动和部署不自动发包。恢复只能由人类命令触发，重复点击不重复执行。允许放弃失败单，不清空其他保护锁。
- 无新依赖、表、后台服务或模型工具；不修改供应商配置。

## 验证

- 使用生产备份的控制账本、绑定密钥、范围和原三张审批，在隔离副本运行旧版，三次批准全部复现发送前失败。
- 随后用新版恢复相同原编号，三笔加密冻结原文逐字节到达本机 HTTP 记录器，重复批准被拒绝；旧结果未知锁逐项不变。传输层仅投递本机，原目标请求数为零。
- 注意：审批展示正文做过 JSON 格式归一化，测试以加密冻结原文为准，而非复制卡片上的空格格式。
- 新增同接口结果未知锁、三种独立参数探测、旧失败单冷启动恢复、已有发送记录或已用次数的拒绝恢复回归；559 项全量回归及发布预检通过。
- 真实 DSH 原生工具运行时、真实 Jev、本机断连靶场：先形成结果未知锁，再批准同接口另一笔未知请求，确认实际发送；原请求重试仍被阻断。该测试不是主模型自主调用测试。
- 界面浏览器回归验证失败旧单出现恢复按钮并提交正确的人类命令。
- 保留试验失败：初次断连未被测试驱动捕获，以及 Jev 将造锁请求挂审而未实际发送；补上显式人类确认并严格要求真实断连后重新执行。没有将“未形成锁”的试验算作通过。

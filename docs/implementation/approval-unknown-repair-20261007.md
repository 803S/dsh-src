# local.121：修复未知请求无法人工放行

## 原因与边界

原会话三张待审单是 `POST /render` 的空正文、`{"values":{}}` 和 `{"template":12345}`。冻结 Jev 判定均为 unknown/unknown/pending，并非已识别高危，也不是降级失败。此前把未知 POST 与写入缺材料等同，卡片禁用批准按钮，导致人工无法接管。

未知不等于安全，也不等于写入。不能按 POST、空正文或接口名字直接自动放行；不会对原资产重放请求或代替用户审批。

## 轻量修复

- Jev 判定说明补充参数格式/类型校验：完整语义仅为有界解析、渲染或校验时选 compute；业务提交、支付、删除、任务触发不适用，仍不明确则保持 unknown。
- 复用现有 `/src-approve` 人类命令，新增 `allow-read`：用户明确确认冻结单笔仅为读取、校验或计算，无持久写入、外发或资源耗尽，才可发送一次。不从备注或模型说明推断授权。
- 仅适用于 unknown/unknown/pending 的 GET/HEAD/OPTIONS/POST 单请求、单次总预算；已识别写入/删除/外发、PUT/PATCH/DELETE、方法与路由改写、编码硬闸不能借用此入口。
- 补齐原冻结单执行说明，重算签名，保留原审批编号、原请求字节及范围绑定。人类确认写入审计，Jev 原始 unknown 判定不改成 low。查看、启动和后台恢复不发送，重复点击不重放。
- 未知 GET 不再由宿主自动填成已确认只读；原有 Jev 已识别读取/计算的人工执行路径保留。
- 卡片新增“确认低影响并放行”，显示空正文或 JSON 字段类型；真正缺写入材料仍明确提示并可拒绝。
- 无新增依赖、表、常驻服务或模型工具；供应商、生产 Jev 配置、范围和凭据不变。

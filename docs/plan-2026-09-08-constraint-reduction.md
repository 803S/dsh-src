## 1. 问题定义

### 1.1 膨胀模式

local.10 → local.66 的迭代模式是：**每次实战暴露一个问题 → 补一段约束**。约束加在五个不同层
（协议、工具描述、lesson、persona、机械编排），且从不回收旧约束。典型例子：

- 中通会话子代理失败 → 加【子 agent 故障处理】663 字符 + src_recover_child（local.57 前）
- Burp 拉包断言错 → 加【Burp MCP 工具面】945 字符
- hackone 双锚点报错 → 加双锚点自愈代码（合理）+ 协议委派段落又改写一遍
- 抓页面撞 SPA 放弃 → 加【已安装能力】反面清单 100+ 字符
- 待办被瞎挂 → 加枚举纪律 864 字符进 src_user_todo 描述（local.65）
- finding 质量差 → 加【漏洞质量标准】658 字符 + submission-quality lesson 11,126 字符（双重约束同一件事）

### 1.2 为什么这是真问题而不只是「感觉重」

1. **常驻成本**：协议 + 工具描述 + persona 是 system prompt 常驻项，每个会话每一轮都占位。
   当前静态约束约 **3 万 tokens**；对 200k 窗口的模型占 15%，且挤占的是注意力最集中区域。
2. **注意力稀释**：约束数量与单条遵从率负相关。实证：协议 45 节、104 处强制措辞的背景下，
   hackone 会话仍然出现系统性双传锚点（5 次）、待办瞎挂（前 local.65 时代）、模型该读 lesson 不读。
   **约束堆叠没有换来行为改善，只换来了 token 成本和规则互相冲突。**
3. **维护面**：同一语义散布多层，改一处漏三处。local.66 的 src_scan_surface 矛盾（协议说开放、
   filter 拦死、委派 prompt 又点名）正是多层约束失同步的产物。
4. **指令性措辞密度**：协议里 禁止×23、必须×34、不得×10、一律×10、不要×25、铁律×2——
   全是最高强制级时等于没有强制级，模型无法区分哪些是真红线。

### 1.3 顺丰会话实证（09-09，session-77038149「顺丰考勤系统渗透测试」）

约束膨胀的代价在本会话完整兑现，四条独立证据：

1. **「medium+ 才能出报告」约束直接吞噬交付**：agent 于 17:51（turn 29）finalize 成功并生成完整报告
   （src_report ×5 全部成功），但协议【漏洞质量标准】要求「报告停止前必须确认存在 medium 及以上」——
   唯一 finding 只有 low，于是 agent **不肯交付已生成的报告**，转身追击 finding-2（未授权工号泄露）
   连续 13 个 turn（18:01→19:18），最后死在供应商故障上。用户等了一整天拿到 0 个可交付成果。
   **如果这条约束不存在，17:56 用户就有一份带完整链路和如实标注的报告。**
2. **上下文膨胀=生存问题**：本会话 compaction/prune ×6（上下文反复爆窗压缩），最后两条消息是
   glm-5.3-flash「AI provider temporarily unavailable … or oversized prompt」。30k 常驻约束 +
   97 facts 图状态 + lesson 注入叠加，小上下文模型直接无法承载。减法不是优化项，是可用性前提。
3. **图有产出、用户看不见**：97 facts / 11 assets / 26 checkpoints / 7+ 未鉴权端点实锤都在图里，
   但用户视角的「产出」= finding 列表（1 条 low）+ 最终报告（未以收尾姿态呈现）≈ 0。
   原生 CLI 至少会写一份总结——结构化编排反而把「文字交付」这个最朴素的产出形态挤没了。
4. **经验注入在错误时机出现**：finalize 成功的返回里还在推 submission-quality（11k 字符 lesson 的提示行）
   ——收官时刻反复提醒质量门槛，正是把 agent 推向「不交付」的力之一。

### 1.4 对照报告实证（无境/Cairn 平台，同目标 09-08 11:32–14:31 仅 3 小时，16 条 finding 全部交付）

用户提供了同目标的外部 agent 报告（~/Downloads/顺丰科技香港中转场签到系统渗透.html），逐条对照：

1. **发现能力没有差距**：Cairn 的 16 条 = public/** 未授权可达逐端点成条（accessLog 可写/问卷配置增删改/供应商名单/岗位布局/Excel 导出）
   + 写入验证（addQuestionnaireConfig 无认证真实落库 id=17）+ XSS 静态/动态链 + 相邻系统（HKAA/AA APP 8 条）。
   我们的 agent 对同一目标发现了同样的 public/* 豁免区端点（7+ 未鉴权实锤在图里），还有一条 **Cairn 没发现的 uc-pwd 万能 JWT**。
2. **差距全在打包与交付**：Cairn 每个未授权端点单独成条、全部标 low、每条带 PoC curl、3 小时交付；
   我们的 agent 被危害链三要素闸把「未授权可达」挡在 finding 外（停在 fact 态），又攥着 low-only 报告不肯交付，最后死于供应商故障。
   **结论：定级严格度与交付量成反比——对手 16 条全 low 照交不误，我们 1 条 low 还觉得拿不出手。**
3. **用户的验收标准就是对照报告的 16 条**（09-09 18:52 用户原话：「这个域名已知的存在16个漏洞，均是未授权即可获取到的」，
   18:23：「全测完了吗？只有1个漏洞？」）——协议的质量闸与用户的验收尺度错位，agent 被夹在中间补差距时断供。
4. **skill/能力调用率 0**：goal 返回的能力牌面 6 项全部送达（clown-src-playbook/src-rules-scraper/wechat-mp-reader/wx-minapp-recon/fofa/playwright），
   整个会话家族（主+子）0 次 src_list_capabilities/src_read_capability/src_run_capability/skill 调用。
   根因：①路由是提示级约束非硬闸；②skill 型调用链摩擦大（读文档→写脚本→审批→resolve 四步 vs curl 一步）；
   ③触发条件「撞到问题才想起」，而 curl/playwright 直连往往「够用了」。讽刺的是 Cairn 也没用任何 skill——纯 playwright+curl，**工具不是差距，交付姿态才是**。
5. **可采纳的打法差距**：Cairn 的「未授权写入→落库回读→删除零残留」三步实证 + WAF 只读预检 + 本地复刻渲染验证，
   正是 clown-src-playbook 应该承载的打法模板；我们的 agent 独立想到了同款（自造数据闭环）但死前未执行完。

### 1.5 响应体黑洞与假阴性实证（09-09 复查深挖，工具层硬伤，v1.3 新增）

用户评审指出 src_http 返回丢响应体，复查代码坐实，并挖出完整事故链：

1. **两处丢弃点坐实**：src_http 放行分支（tools/index.js:1623）只回 `{method, path, status, approval, reason}`；
   src_resolve_approval 重放分支（store.js:459-460）`responseStatus = response.status` 同样丢 body；render 两处都只打状态码。
   顺丰家族 9 会话（主+8 子代理）共 **1000 次工具调用，src_http 103 次**（主会话 0 次纯编排、子代理侧 103 次；
   用户口径「710 次」恰为 8 个子代理侧调用总和，290+710=1000）+ **13 个审批重放，没有一次见到响应体**。
   修法便宜：proxiedFetch 三条路径（直连 fetch Response / 代理 emulatedResponse / legacy 降级同款封装，src.js:687）
   返回值统一支持 `.text()`，代理路径连 body 都已缓冲好（4MB 上限，src.js:822-826）——**两个调用点各 1-2 行**。
   丢的不是一个字段，是 agent 唯一的取证与诊断来源（→ 争议点 #17）。
2. **盲发重试与错误归因链条**：agent 拿不到 body 只能从状态码瞎猜——对 415 连发 5 发变体
   （multipart 三种字段名 + octet-stream，approval-6/9/10/11/12），最后写入图里的终局结论是
   「端点存在上传类型白名单，未授权写入不成立」。而 fact-31 早已写明「批准后**响应体分析是 evidence 关键**」
   ——关键证据被工具层结构性丢弃，重试策略退化为盲发。
3. **假阴性实锤（Content-Type）**：approval-8 原始调用（子代理 ce127543）POST JSON 字符串体
   **未带 `Content-Type: application/json` 头**（fetch 对字符串 body 不自动加）→ Spring 415；
   对照报告 Cairn 同端点同 JSON 带头 → **200 {"succ":"ok"}**（其 3.1 accessLog PoC）。
   即「schedule/upload + accessLog 未授权写入不成立」的结论高度可疑，属**测试手法缺陷造成的假阴性**而非端点行为。
   顺丰平台 09-14 恢复后带 Content-Type 重测这两端点，可能是白捡的 finding。
4. **lesson 读用率补充实测**：家族 src_read_lesson 共 9 次，全部是 scope-confirmation/sms-bomb/token-lifecycle
   三件套在 3 个会话各机械注入一遍，主动决策引用仍为 0——「经验进 lesson 不如进工具返回值」的载体判断再+1（→ 争议点 #18）。

## 3. 判定标准：约束四问

每条约束处置前过四问（论证时以此为准绳，避免拍脑袋）：

1. **它防的是已发生的真问题吗？**（有会话证据）还是想象中的问题？
2. **它的最小表达形式是什么？** 同一语义能不能用更少字符/更低层（代码硬闸 > 工具描述 > 协议 > lesson）表达？
3. **它有唯一家吗？** 同一语义是否已在别的层表达？（重复 = 两处都要维护 = 必然失同步）
4. **违反它的后果是可自愈的吗？** 服务端能拦/能报错教学的（闸类），提示词可以更短——
   模型错了会被闸纠正并学到；闸拦不住的（行为倾向类）才需要提示词常驻。

配套的**表达层级优先序**（越上越优先）：

```
代码硬闸（机械、零 token、不可绕）> 工具描述（用时可见）> lesson（按需加载、可搜索）> 协议常驻文本（最贵）
```

## 8. 争议点清单（多轮论证的主战场）

### #1 触发器引擎拆不拆
- **拆（推荐）**：它是「发现什么就加编排」模式的唯一幸存实例；`when` 描述+能力盘点+枚举纪律已覆盖同一语义三层；拆掉删 ~40 行引擎+yaml 字段+合成事件+fold case+测试，维护面显著缩小。风险：小程序线退化为「agent 看清单自己想起来」——但 local.65 的枚举纪律明确写了「本机微信包扫描」是 agent 本职，语义有承接。
- **留**：它是唯一被实战验证过的确定性编排闭环（local.61/62 headless e2e 逐字验证过）；确定性 > 概率性，agent 忘了看清单就漏。风险：死编排再膨胀的口子保留着。
- **折中（Y）**：引擎留、声明删，等第二次真实需要再启用。

### #11 medium+ 报告门槛（顺丰实证新增，优先级最高）
- **现状**：协议【漏洞质量标准】「报告停止前必须确认存在 medium 及以上、有可复现 POC…的 finding」
  + src_report/finalize 的 warning 措辞（「仅存在 low 级 finding…建议继续推进」）。
- **删（推荐）**：顺丰会话实证它把 agent 变成不交付的完美主义——报告已生成却不肯给用户，追击 80+ 分钟后死于供应商。
  对照报告 16 条全 low 照样打包交付。改为：报告随时可出、low-only 如实标注原因（SIT/无登录态/平台停服），是否继续追由用户拍板（交付后建 src_user_todo 征询）。
- **留**：删掉后模型可能轻松交付低质量报告凑数。反驭：危害链三要素准入闸仍在（服务端强制），凑数的 finding 本就入不了库；
  报告门槛防的是「态度」不是「质量」，而态度问题用户一眼能看穿。

### #11b finding 准入闸放宽（对照报告实证新增，优先级同 #11）
- **现状**：危害链三要素作为 finding 入库门槛，「未授权可达端点」类因无实际损失证据被拒入库（顺丰 7+ 端点停在 fact 态）。
- **改（推荐）**：**未授权可达+可复现 PoC 即可入库（low 起评）**；危害链三要素降级为「升危依据」——
  组合出实际损失证据时升 medium+，而不是拦着不入库。依据：对照报告 16 条全是「未授权可达」级，无一有实际损失实锤，
  但这正是 SRC 实际可提交的粒度；数量凑链本身是合法策略。
- **留**：会凑数刷 finding 污染报告。反驭：severity 字段如实标 low，用户看报告自己加权；宁可多收窄进（UI 可筛），不可漏交。

### #12 图状态输出的预算（顺丰实证新增）
- **现状**：src_state/src_report 渲染 97-fact 图全量文本；会话 compaction ×6、终局 oversized prompt。
- **改（推荐）**：src_state 输出分级——active intents 全量 + facts 只出最近 N 条与 P≥8 的，其余给计数+指引
  （src_graph 按需查询）；src_report 的探索链路节同样截断。这是「输出侧减法」，与输入侧瘦身同轮做。

### #13 finalize 后必须交付收尾（顺丰实证新增）
- **现状**：协议【终止】节无「交付即停」语义：agent finalize+report 后又自行开新 intent 继续挖（用户没有叫停它）。
- **改（推荐）**：finalize 成功=本 engagement 交付完成，继续挖掘必须先交付报告并征询用户（一句话入协议【终止】节）。

### #17 src_http / src_resolve_approval 响应体透传（09-09 实证新增，优先级最高档，v1.3）
- **现状**：两处放行点（tools/index.js:1623、store.js:459）只回状态码；顺丰家族 103 次 src_http + 13 次重放无一见到响应体（§1.5）。
- **做（推荐，轮 1，独立 commit）**：两调用点各 1-2 行读取 body 透传（proxiedFetch 三路径已统一支持 `.text()`，无需规格化改造）；
  同轮加四件防护：①截断（默认 2KB，仅 text/json 类响应体，二进制/图片只回长度，参数可放宽）
  ②去重：同 host+method+path 的**响应哈希（status+body）**重复时只回 hash+长度，请求可带 full 参数强制返回完整体
  （不能用请求 body-hash 做键——同路径前后两次响应不同正是越权写入验证的关键信号，误吞=假阴性）
  ③凭证/PII 掩码（复用 credentials.js stripCredentialHeaders 模式扩正则清单）
  ④JSON body 且未显式指定 Content-Type 时自动补 application/json——一行硬闸，直接消灭 §1.5 第 3 条整类假阴性（415×5 盲发的根因），#18 注脚只兜剩余形态问题。
  **resolve_approval 重放透传是主修点不是附带**——重放的恰是审批过的高价值请求，finding PoC 就靠这份响应
  （fact-31 原话「响应体分析是 evidence 关键」）。
- **不做**：担心 body 泄漏凭证回上下文。反驳：截断+掩码正为此设计；实证代价（盲发×5+Content-Type 假阴性+错误归因入图）远大于泄漏风险。

### #18 阴性判定回炉注脚（加法轮实证新增，v1.3）
- **现状**：src_record_research negative 落盘时无任何自查提醒；顺丰 415×5 盲发 +「上传白名单」错误归因直接入图。
- **做（推荐，轮 1，~10 行）**：src_record_research（negative）工具返回值追加两行固定自查清单——
  「①是否已换请求形态重试（方法/Content-Type/参数名/编码/路径变体）？②失败是否可能源于本机通道或请求构造而非端点行为？」
  载体在工具返回值（闸类，模型错了会被纠正）而非 lesson——lesson 读用率 0 已实证（§1.5 第 4 条）。

## 11. 防再膨胀机制（本轮减法的「不复发」保险）

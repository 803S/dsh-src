# 签名墙不是终点：签名体系本身就是漏洞面（key 泄露→破解→接管）

## 触发场景
- 接口被客户端签名保护（mtgsig/H5guard/签名防篡改/X-Sign 等），agent 无法直接构造请求，倾向绕路收尾 blocked。
- 开发视角常见误区：签名越复杂越放心，服务端不再做归属/权限二次校验——签名体系一旦要素泄露即整条防线失效。

## 核心经验（SRC 审核视角）
签名特别复杂的接口恰恰值得审计签名体系本身：**签名复杂 → 开发信任签名 → 服务端盲信不二次校验 → key/secret/算法泄露 → 签名被破解 → 任意账号接管/越权/未授权高危**。被签名墙挡住 ≠ 方向终止，签名墙本身是审计对象。

## 审计套路（合法且有界）
1. **客户端产物搜签名密钥**：APK DEX（droidasc findrefs 搜 sign_key/appsecret/aes_key/hmac/secret/加密常量）、小程序/H5 反编译产物（wedecode 产物 grep 签名函数与 key 字面量）——「无硬编码 JWT」不足以收口，签名密钥与签名函数定位是必做项。
2. **签名函数可复现性判断**：从反编译产物定位签名装配函数，判断算法是否可离线复现（弱混淆 JS 常可；强混淆 VM 记录位置与形态即可，不强行逆向）。
3. **可复现即测服务端盲信**：用可复现签名能力重签**变异参数**（换用户 id/订单 id），看服务端是否还做归属二次校验——盲信即高危 finding。
4. **不可复现则借道真实客户端**：经真机/模拟器/小程序 Burp 抓包取合法签名请求，只做覆盖面对比（签名不覆盖的参数直接改）与重放变异；hook 重签（Frida 在签名函数调用点后改参数）只在授权明确时做，不大规模对外使用。

## 收录标准
危害链：①签名要素（key/算法）可从客户端产物提取或可复现 ②服务端对变异参数不二次校验归属 ③实际损失（越权读/接管/未授权写）。三环齐才成 finding；只有①时如实记 fact（签名体系暴露面），不下高危结论。

## 红线
- 逆签名算法仅用于**授权范围内**验证服务端盲信；禁止大规模对外生成签名、批量伪造设备指纹（超出授权即违规）。
- 重放/重签只做有界验证（≤10 变体），撞风控（异常 403/429/验证码突增）立即停手。

## 教训
被墙挡住时先问「墙本身是不是漏洞面」——不要只绕路。签名墙的覆盖缺口应登记为 gap 并在后续轮审计其本身，而不是标记 blocked 即终止。
